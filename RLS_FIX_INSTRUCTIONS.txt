RLS POLICY FIX GUIDE
===================

ERROR MESSAGE:
"new row violates row-level security policy for table 'tickets'"

This error occurs when trying to save a new ticket.

ROOT CAUSE:
Row-Level Security (RLS) policies on the tickets table are blocking INSERT operations.
This is typically because:
1. No INSERT policy exists for authenticated users
2. RLS is enabled but policies are too restrictive
3. RLS policies reference columns that don't exist or are NULL

IF THE FIX DOESN'T WORK:
=======================

Try these additional checks:

1. Check if 'user_role' column exists in profiles table:
   SELECT column_name FROM information_schema.columns 
   WHERE table_name = 'profiles' AND column_name = 'user_role';
   
   If missing, add it:
   ALTER TABLE public.profiles ADD COLUMN user_role TEXT DEFAULT 'user';

2. Check if 'processed_by' column exists in tickets table:
   SELECT column_name FROM information_schema.columns 
   WHERE table_name = 'tickets' AND column_name = 'processed_by';
   
   If missing, add it:
   ALTER TABLE public.tickets ADD COLUMN processed_by TEXT;

3. Verify RLS is actually enabled:
   SELECT tablename, rowsecurity FROM pg_tables 
   WHERE tablename = 'tickets';
   
   Should return: rowsecurity = true

4. Check what policies currently exist:
   SELECT policyname FROM pg_policies WHERE tablename = 'tickets';

5. Try the NUCLEAR OPTION (last resort - SECURITY RISK):
   ALTER TABLE public.tickets DISABLE ROW LEVEL SECURITY;
   
   ⚠️ WARNING: This disables all row-level security!
   Only use for testing, then re-enable and fix properly.


UNDERSTANDING THE POLICIES:
===========================

The fix creates 4 simple policies:

1. "authenticated_insert" 
   - Who: Any logged-in user (authenticated)
   - Action: Can INSERT (create) new tickets
   - Condition: None (WITH CHECK true = always allow)

2. "authenticated_select"
   - Who: Any logged-in user (authenticated)
   - Action: Can SELECT (view) tickets
   - Condition: None (USING true = always allow)

3. "authenticated_update"
   - Who: Supervisors and admins only
   - Action: Can UPDATE (edit) existing tickets
   - Condition: user_role must be 'supervisor' or 'admin'

4. "authenticated_delete"
   - Who: Supervisors and admins only
   - Action: Can DELETE tickets
   - Condition: user_role must be 'supervisor' or 'admin'

STILL HAVING ISSUES?
====================

Common problems and solutions:

Problem 1: Still getting RLS error after running fix
Solution: The 'user_role' column might not exist in profiles table
  → Run: ALTER TABLE public.profiles ADD COLUMN user_role TEXT DEFAULT 'user';

Problem 2: Can't delete tickets even as supervisor
Solution: The delete policy might need adjustment
  → Run: CREATE POLICY "fix_delete" ON public.tickets FOR DELETE 
         TO authenticated USING (true);

Problem 3: Performance issues after applying policies
Solution: Add indexes to frequently filtered columns
  → Run: CREATE INDEX IF NOT EXISTS idx_tickets_user_role 
         ON public.profiles(user_role);

Problem 4: Policies not taking effect
Solution: Browser cache might be causing issues
  → Clear browser cache and try again
  → Or logout/login to refresh authentication tokens
